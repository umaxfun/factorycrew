# 03 — Blueprint tooling and sources (for Kira)

Scope: libraries to encode/decode/build blueprint strings, blueprint sharing sites (API / scrapeability), editors and renderers for previews, image/pixel-art generators, and blueprint books / 2.0 parameterised blueprints. Data gathered 2026-10-28 via `gh api repos/...` (stars, license, last push), raw source files, and site fetches. "Last push" = GitHub `pushed_at`.

Kira constraints that drive the verdicts: Python is stdlib-only and sandboxed; the mod places ghosts via `LuaItemStack.import_stack` + `build_blueprint`; so anything that emits a valid 2.0 blueprint string from stdlib Python is directly useful, and anything heavy (numpy, PIL, Node, JVM) is idea-only or an offline tool.

Background fact used throughout: a blueprint string is `"0"` + base64(zlib-deflate(JSON)). That is fully doable with Python stdlib (`json`, `zlib`, `base64`), so the hard part is never the codec; it is the entity schema (names, direction encoding, 2.0 field changes, quality, wires).

Notes
- No mature stdlib-only Python library with a full 2.0 entity model exists. The practical path is: stdlib codec (≈10 lines, or vendor pierre-dejoue) + Kira's own small entity emitter, checked against the vendored 2.0 schemas and against draftsman offline.
- 2.0 changes Kira's emitter must handle (confirmed by demipixel's fix and the schemas): 16-step `direction` (old 8-step values ×2), `quality` fields, `wires` array replacing `connections`, elevated rails / new rail entities, and the 64-bit `version` number (four 16-bit fields major/minor/patch/dev, so 2.0.x starts at `2<<48` = 562949953421312; the [wiki](https://wiki.factorio.com/Blueprint_string_format) links its "Version string format" page for this).
- From the [wiki string-format page](https://wiki.factorio.com/Blueprint_string_format): the version byte is still `0` through 2.0; zlib level 9; "as of 2.0 the game can also import the uncompressed JSON blueprint string directly"; and mod Lua has `helpers.decode_string` / `helpers.json_to_table` (plus the `encode_string` / `table_to_json` counterparts). So Kira's mod can do the codec in Lua, and Python can hand over plain JSON. Not verified: whether `import_stack` accepts raw JSON the way the GUI does. Test it in-game.
- Kira may not need strings at all: the 2.1.24 runtime API ([runtime-api.json](https://lua-api.factorio.com/latest/runtime-api.json)) exposes `LuaItemCommon.set_blueprint_entities` / `set_blueprint_tiles` / `build_blueprint`. The mod can fill a blueprint item from a Lua table that Python produced, then build it.

## 4. Image-to-blueprint, pixel art, lamp art, text

2.0 makes this much simpler. The 2.0 lamp schema ([`schemas/2.0.0/entity/lamp.json`](https://github.com/redruin1/factorio-blueprint-schemas/blob/main/schemas/2.0.0/entity/lamp.json)) has a fixed RGB `color` (ignored only if `control_behavior.use_colors` is true) plus `always_on`. So lamp art is one lamp entity per pixel, with no combinators or signal palette. Text gets the 2.0 `display-panel` entity (`text`, `icon`, `always_show`, `show_in_chart`). Tile art is a `tiles[]` array (refined-concrete colour variants in vanilla; modded tiles need the mod).

## 5. Books, common builds, classification, 2.0 parameterised blueprints

What parameterisation is: from 2.0.7, a blueprint's `parameters[]` holds `id` parameters (replace a signal/item/recipe id; can be `ingredient-of` an earlier parameter; optional `quality-condition`) and `number` parameters (replace a numeric constant; optional `variable` + `formula`, e.g. `x*2`, or stack-size/rocket-capacity of a chosen parameter). Placeholders are the virtual signals `parameter-0`…`parameter-9`. When the player places the print by hand, the game asks for the values ([wiki: Blueprint § Parameterisation](https://wiki.factorio.com/Blueprint); schema `$defs/id-parameter`, `$defs/number-parameter` in [2.0.0/blueprint.json](https://github.com/redruin1/factorio-blueprint-schemas/blob/main/schemas/2.0.0/blueprint.json)).

Gap that matters for Kira: the 2.1.24 runtime API has no method or argument to supply parameter values. `build_blueprint{surface, force, position, direction, build_mode, skip_fog_of_war, by_player, raise_built}` takes no parameter values, and no `*blueprint_param*` method exists on `LuaItemCommon`, `LuaRecord` or `LuaItemStack` (checked in `runtime-api.json`). So Kira has to resolve parameters herself before building: substitute `parameter-N` everywhere, resolve `ingredient-of` from live recipe prototypes, and evaluate formulas. What `build_blueprint` does with an unresolved parameterised print was not verified; test it in-game.

## Best picks for Kira

1. **factorio.school / Factorio Prints REST API → call-as-is.** It is the only public, unauthenticated, searchable blueprint API. Kira tool `search_prints(text|entity|recipe|tag)` → `GET https://www.factorio.school/api/blueprintSummaries/search/page/1?...`, then `GET /api/blueprint/{key}`, decode with stdlib, and filter by "all prototypes exist in this save" (essential for Nullius; `text=nullius` returns only 3 prints). Respect robots (`ai-train=no`, `use=reference`): on-demand only, low rate, honest UA, cache results, credit the author/URL to the player.
2. **Recursive Blueprints+ `parameterization.lua` (MIT) → vendor into the mod.** It solves resolving 2.0 parameterised prints from script, which the runtime API doesn't do. Extend it with the print's own `parameters[]` (`ingredient-of` via `prototypes.recipe`, formulas via a tiny safe evaluator), then `set_blueprint_entities` → `build_blueprint`.
3. **redruin1/factorio-blueprint-schemas (MIT) → vendor as the format spec and test corpus; draftsman → offline oracle.** Ship the 2.0 JSON schemas (or a trimmed field table) with Kira so the LLM and the Python emitter use correct 2.0 field names (16-way `direction`, `wires`, `quality`, `parameters`, lamp `color`, `display-panel` `text`). Round-trip their `test/examples` strings in CI. Use draftsman (heavy deps, outside the sandbox) only in dev to cross-check emitted prints.
4. **Stdlib codec + summarizer → port pierre-dejoue/factorio-blueprints (MIT, zero deps).** Decode/encode, version readout, and contents summary for anything the player pastes. Pair it with a port of FBE's link resolver (pastebin/gist/factoriobin `…/blueprint.txt` + `/info.json`/factorio.school URL → raw string) so "build this link" works.
5. **Preview: FBE fork share link → call-as-is; piebro-style SVG → port the idea.** For vanilla-ish prints, give the player `https://fbe.factorygamefan.com/#source=<string>` (no server, never expires; 2.0 + Space Age). For modded prints, where sprites will be missing, render a schematic SVG in stdlib Python from entity footprints and connections, piebro-style. In-game ghosts or a cursor-stack import are the zero-dependency fallback. FBSR is the high-fidelity modded renderer, but only as an optional JVM sidecar.

Also cheap and worth doing: lamp/tile/text art needs no library in 2.0. Emit `small-lamp` with `color` + `always_on`, `tiles[]`, or `display-panel.text` directly. MagicManMe/ImageToBP (no license) is a model of the approach only.

Not verified / open: whether `import_stack` accepts raw uncompressed JSON; how `build_blueprint` treats an unresolved parameterised print; whether FBE renders unknown modded entities gracefully; the correct value format for the factorio.school `mod=` filter.

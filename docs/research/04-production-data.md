# 04 — Production planning & game data (for Kira)

Scope: ratio/production calculators and their solvers, modded game-data extraction, and machine-readable Factorio API docs. Goal: find solved problems Kira can borrow. Kira constraints that shape the verdicts: live save access via Lua (`prototypes` global in 2.0), Python **stdlib-only** in a sandbox (no numpy/scipy/PuLP/GLPK), output is ghost entities.

Method: GitHub repo API (`gh api repos/...`) for license/stars/last push; source files read via raw.githubusercontent.com. Stars/dates captured 2026-10-28. GitHub search API was rate-limited (shared with parallel researchers), so discovery leaned on known project names + direct repo lookups.

Verdict key: **port** = re-implement the algorithm in Kira's Python; **vendor** = copy code/data as-is; **call-as-is** = use the running tool/endpoint; **idea-only** = borrow design, not code; **skip**.

## Key takeaway (so far)

All serious calculators reduce multi-recipe chains to one linear program: variables = recipe rates (machines), one row per item = net production balance, plus slack variables for surplus/imports, minimising a cost vector. Kirk McDonald's calculator does this with a ~190-line **exact rational dense-tableau simplex** (`simplex.js`) that ports almost line-for-line to Python `fractions.Fraction` — the clean pure-stdlib path for Kira.

Notes on the math, common to all LP solvers above:
- Variables: recipe rate `x_r ≥ 0` (crafts/s or machines). Item balance per item `i`: `Σ_r (out_ri − in_ri)·x_r + import_i − surplus_i = target_i`. Byproducts (heavy oil, recycling returns) are simply negative/positive entries; cycles need no special casing in an LP.
- Modules/beacons/productivity/quality are **pre-applied** to each recipe's coefficients before the LP (FactorioLab `adjustment.ts`, FP and Helmod do the same per line). Productivity multiplies only `amount − ignored_by_productivity`; it is capped by `recipe.maximum_productivity` (2.0, default +300%); speed/consumption floor at 20%. Quality turns one item into N item-ids and adds quality-upgrade outputs with probabilities (`quality.next_probability`) — still linear.
- Preference between alternatives (e.g. cracking vs. burning, which recipe for an item) is expressed as costs: FactorioLab penalties, FP weight vector, Kirk's lexicographic priority costs.
- A pure-Python dense rational simplex (Kirk-style; `simplex()` uses Dantzig's most-negative-column rule — add Bland's rule as an anti-cycling fallback when porting) is fine for the problem sizes involved (tens–low hundreds of recipes). Local micro-benchmark (python3 stdlib, this machine): 20 full Gauss-Jordan pivots on a 150×300 `Fraction` tableau at ~5% density took 0.11 s, so a typical plan solves well under a second. Denominators can grow on dense/pathological inputs; a float tableau with 1e‑9 tolerance (FP's `SimplexTableau.lua` uses 1e‑10) is the fallback.

## B. Game-data extraction from a modded install

Three strategies exist, in decreasing fidelity for Kira:

1. **Runtime read inside the live save** (Kira's native path): the 2.0 global `prototypes` (`LuaPrototypes`, 57 attributes e.g. `prototypes.recipe`, `prototypes.quality`, plus `get_entity_filtered`/`get_recipe_filtered`) sees the *exact* final modded data, including Nullius, with no extra process. Serialise with `helpers.table_to_json` and either return it over RCON or `helpers.write_file` to `script-output/` (both confirmed in `runtime-api.json` 2.1.24 `LuaHelpers` methods; in 1.1 these were on `game.*`). Caveat: runtime prototypes expose computed values (e.g. `LuaRecipePrototype.energy`, `maximum_productivity`, `allowed_effects`, `surface_conditions`) but *not* every raw data.raw field or graphics.
2. **`factorio --dump-data`**: "dumps data.raw as JSON to the script output folder and exits" ([wiki](https://wiki.factorio.com/Command_line_parameters)); companions `--dump-prototype-locale` (names/descriptions) and `--dump-icon-sprites` (PNGs). Uses the user's enabled mods. Must be separate runs and can collide with a running game's lock — run with an isolated write-data dir (alecraso `src/data-layer/dump.ts`).
3. **Re-implement the data stage outside the game** (YAFC `Yafc.Parser/LuaContext.cs` + `FactorioDataSource.cs` reading `mod-list.json` and zipped mods; draftsman's lupa pipeline; Kirk's FactorioLoaderLib). Powerful but brittle against mods that rely on engine behaviour. Not needed by Kira since she has the live game.

## Best picks for Kira

1. **Port Kirk McDonald's rational simplex to stdlib Python** (`simplex.js`, `solve.js`, `matrix.js`, `rational.js`; Apache‑2.0, keep the notice). Plan: `kira/lp.py` with a dense `Fraction` tableau, phase‑1 `eliminate_negative_bases`, Dantzig pivot + Bland fallback; `kira/plan.py` builds rows = items, cols = recipes + surplus + import slacks, exactly like `solve.js`'s `[surplus][pseudo][tax][recipes][result][cost]` layout. Keep Kirk's trick of tree-walking acyclic single-product parts and only LP-ing the cyclic/multi-product core (oil cracking, Nullius gas loops, recycling). Exact fractions give clean "7.5 assemblers" answers. ~600 LOC, unit-test against Kirk's live calculator on vanilla/Space Age.
2. **Port FactorioLab's recipe-adjustment rules + cost model** (`src/state/adjustment.ts`, `src/solver/solver.ts`; MIT). Pre-apply modules/beacons to each recipe before the LP: additive effects, beacon `profile[n]` scaling, 20% floor on speed/consumption, productivity capped at `recipe.maximum_productivity` and applied only to `amount − ignored_by_productivity`, quality fan-out by `next_probability`. In the LP, give every item penalised `unproduceable`/`excluded`/`surplus` slack vars so the solve never fails outright; Kira then reports "needs import of X/s" instead of "infeasible". Borrow YAFC's idea of reporting *which* loop link needed slack.
3. **Vendor Foreman2's export-mod field list into Kira's Lua reader** (`foremanexport_2.0.0/instrument-control.lua`; BlueOak‑1.0.0). Read `prototypes.recipe/item/fluid/quality/technology` + `get_entity_filtered{{filter='crafting-category'}}` live, emit one compact JSON via `helpers.table_to_json` (normalised: recipes with per-product `p_amount`, machines by category with speed/module slots/allowed effects, qualities with `next`/`next_probability`, planets via `surface_conditions`). This is the only data source that is guaranteed to match the player's Nullius version; FactorioLab's `nls` dataset is 1.1-era.
4. **Version-pinned API lookup tool from the official JSON docs** (C1/C2; pattern from alecraso `src/api-docs/index.ts`). Download `https://lua-api.factorio.com/<game_version>/runtime-api.json` and `prototype-api.json` once, build a name → (signature, description, stage) index in stdlib Python, and expose `lookup_api("LuaEntity::get_recipe")` to the LLM. Optionally run FMTK `fmtk docs --online <ver> --pdump data-raw-dump.json` at dev time and lint generated Lua with LuaLS `--check`.
5. **Port Rate Calculator's live-rate audit** (`scripts/calc-util.lua`; MIT). After ghosts are built, read the real entities in an area (`entity.get_recipe()`, `crafting_speed`, `productivity_bonus`, `get_max_energy_usage(quality)`), compute actual max rates keyed `type/name/quality`, and diff them against the plan. This closes the loop: plan (LP) → ghosts → verify. Factory Planner's objective weights (`simplex_engine.lua`) are the backup reference if Kira's cost tuning misbehaves.

Not recommended: GLPK/OR-Tools based solvers as code (not stdlib), alecraso's `chain.ts` tree expansion for anything with byproducts (it does not credit them back), Kirk's `factorio-tools` (no license, pre-2.0).
